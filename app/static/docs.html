UNDERSTAND THE BACKEND

A small stack. A job you can follow.

The API accepts work; the worker performs it. These are separate Python processes sharing one SQLite database and data directory.

HTTP & validation

Uvicorn runs the server. FastAPI maps URLs to Python functions and exposes OpenAPI. Starlette provides underlying web responses and static-file support. Pydantic checks typed inputs; email-validator validates email format, not mailbox ownership.

Code: app/main.py and app/schemas.py.

Persistence & coordination

SQLite, through Python's built-in sqlite3, stores jobs and recipient outcomes. Short transactions and indexes keep polling practical. filelock allows one worker per data directory and prevents competing ZIP builders.

Code: app/db.py, app/service.py, and app/worker.py.

PDF creation & preview

ReportLab draws vector A4 landscape certificates, embeds fonts, wraps long text, and writes PDFs atomically. PDF.js only displays those finished files in the browser. Classic, Modern, and Minimal share the same generation pipeline.

Code: app/renderer.py, app/templates.py, and app/static/app.js.

Testing & documentation

pytest runs tests; HTTPX supports API calls in tests; pypdf checks actual PDF text/pages. Ruff formats/lints Python. Swagger UI powers the explorer below; Prettier formats frontend/docs source. Node is needed only to update development assets.

No Celery, Redis, React build, or paid PDF service is required.
1. SubmitJSON & recipient validation→ 2. PersistJob + rows in SQLite→ 3. GenerateOne recipient at a time→ 4. RetrieveProgress, PDF & ZIP

A worker restart requeues interrupted PROCESSING rows. A crash after writing a PDF but before committing success can regenerate that PDF at its stable UUID path. This is at-least-once processing, not an exactly-once filesystem/database transaction.

REQUEST & RESPONSE GUIDE

Know exactly what to send.

POST /api/jobs needs two top-level fields: certificate and a nonempty recipients list. Unknown fields are rejected. Select an example in the explorer to try either a fully valid batch or isolated row failures.

Shared certificate fields
  • organization — required issuing organization.
  • course — required course/event title.
  • signatory — required printed issuer name.
  • issued_on — required real calendar date; send YYYY-MM-DD.
  • title — optional; defaults to Certificate of Completion.
  • signatory_role — optional; defaults to Program Director.
  • template — optional classic / modern / minimal; defaults to classic.

All shared text fields are trimmed, 1–120 characters, with font coverage checked before a job is accepted. One design applies to every recipient.

Recipient fields & row validation
  • name — required string, 1–120 trimmed characters.
  • email — optional valid address or null. Omit if unavailable; an empty string is invalid. Duplicate non-null addresses are invalid within the job, ignoring case.
  • reference — optional string or null, up to 80 characters; printed on the PDF.

Invalid rows retain their original zero-based index. Structurally invalid input is INVALID; unsupported recipient font glyphs become FAILED during rendering. Other rows continue. Email is metadata; certificates are not emailed.

Headers, limits & identifiers
  • Content-Type: application/json for submissions.
  • X-API-Key when CERT_API_KEY is configured; use Authorize below.
  • Idempotency-Key is optional for POST jobs; 1–128 characters. An identical retry returns the existing job; changed data returns 409. Use a fresh key for new work.
  • Default limits: 10,000 recipients and 8 MiB body bytes. Both apply; the hard schema cap is 100,000 rows.
  • job_id is the batch UUID. A recipient's id is the certificate UUID. Invalid syntax gives 422; unknown valid IDs give 404.
Read a job response correctly
  • total — every submitted recipient row.
  • succeeded — completed PDFs.
  • failed — all unsuccessful outcomes, including invalid input.
  • invalid — subset of failed; do not add it again.
  • pending — rows without a final outcome.
  • progress_percent — processed outcomes / total × 100, rounded to two decimals.
  • created_at and finished_at — UTC ISO timestamps; finished_at is null until terminal.
  • certificate — normalized shared fields and design.

202 means accepted. 100% means every row has an outcome, not that all succeeded. An idempotent retry can return an already-finished job, still with HTTP 202.

Pagination, preview & download behavior
  • Job history: newest first, limit 1–100 (default 25), offset ≥ 0.
  • Recipients: input order, limit 1–500 (default 100), offset ≥ 0. Filter by status or attention=true, not both. Page total counts matching rows.
  • Only COMPLETED rows have a relative download_url. Add it to the base URL. A ready individual PDF is available before its batch finishes.
  • Preview returns actual application/pdf bytes inline; download returns an attachment.
  • ZIP requires pending = 0 and at least one success; it omits failures. UUID filenames avoid duplicate-name collisions. There is no ZIP error manifest.
  • The first ZIP request builds on disk; later requests reuse it. The lock waits up to 60 seconds before 503. Allow appropriate client timeouts.
Common mistakes & troubleshooting
  • Stuck QUEUED: check the worker terminal and that both processes share CERT_DATA_DIR.
  • Bad shared fields: fix the request's 422 detail rather than expecting per-row recovery.
  • All rows invalid: FAILED at 100% is correct; there is no ZIP.
  • 409 after retry: inspect detail. A reused key with changed data differs from a file that is not ready.
  • Results missing: request the next page or remove filters.
  • 410: inspect storage; a missing PDF is not a live-HTML formatting problem.
  • No cancellation, deletion, email dispatch, or certificate-verification endpoint is implemented.

Application errors usually have a string detail; framework validation errors have a list with location/type/message. Full repository guides: docs/API_REFERENCE.md and docs/TECHNICAL_GUIDE.md.

THE CONTRACT

Clear rules. No surprising failures.

Validation has two levels.

Bad shared fields, unknown templates, an empty list, or too many recipients reject the request with 422. A malformed recipient only fails that row; valid recipients still generate.

Each recipient needs a name (1–120 characters). email is optional but must be valid and unique within the batch. reference is optional (up to 80 characters). Extra fields are rejected. Packaged fonts support accented Latin text; unsupported glyphs fail clearly.

Progress includes failed rows.

pending = total − succeeded − failed. invalid is a subset of failed; do not add them together. A batch with all-invalid rows immediately returns FAILED at 100%.

COMPLETED means all successful. COMPLETED_WITH_ERRORS means mixed outcomes. FAILED means none succeeded. A rendering error does not stop the rest of the batch.

Safe retries & optional auth.

Send Idempotency-Key with a job to retry safely. The same key and payload return the same job; changed data or template returns 409. Use a fresh key for a new batch.

Local setup has no authentication. If CERT_API_KEY is set, click Authorize in the explorer and enter its value. Clients send it as X-API-Key. Use HTTPS for public deployments; the docs are not a user-management system.

Errors you can act on.

  • 401 Missing or incorrect configured key.
  • 404 Unknown job or certificate ID.
  • 409 Result not ready, no successes, or idempotency conflict.
  • 410 A stored certificate file is missing.
  • 413 Request body too large.
  • 422 Invalid request or query parameters.
  • 503 ZIP build is locked; retry shortly.

/health checks the API and database only. It does not prove that a worker is running.
